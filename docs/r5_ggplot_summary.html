The Grammar of Graphics

  • From Leland Wilkinson to Hadley Wickham
ggplot(data = <DATA>) +
  <GEOM_FUNCTION>(mapping = aes(<VARIABLES>))
  • data: a data frame, supplied to ggplot()
  • geom: the shape you want to plot — geom_point(), geom_col(), geom_line(), etc.
  • aes: the mapping from data to that shape, inside aes()
  • Layers connect with +

DEMO: A Minimal Plot

library(tidyverse)
gapminder <- read_csv("gapminder.csv")
gapminder07 <- gapminder |> filter(year == 2007)
ggplot(gapminder07) +
  geom_point(aes(x = gdpPercap, y = lifeExp))

Getting Your Data Ready

Categorical Data: Factors

  • R stores categorical variables as factors — a vector with a fixed set of levels
  • ggplot uses factor levels to decide legend order, axis order, etc.
  • Without factors, categories are sorted alphabetically — not always what you want

EXAMPLE: Reordering with Factors

gapminder07 |>
  mutate(continent = factor(continent,
    levels = c("Oceania", "Americas", "Europe", "Asia", "Africa"))) |>
  ggplot() +
  geom_boxplot(aes(x = continent, y = lifeExp))

EXAMPLE 3: Small Multiples

With a partner, try to understand what’s happening in this code

ggplot(gapminder07) +
  geom_point(aes(x = gdpPercap, y = lifeExp, size = pop,
                 col = continent), alpha = 0.6) +
  facet_wrap(~continent) +
  labs(
    title = "Life Expectancy vs. GDP per Capita (2007)",
    subtitle = "Point size reflects population",
    x = "GDP per capita", y = "Life expectancy"
  ) +
  theme_minimal() +
  theme(legend.position = "bottom")
  • Once you understand the code, look at the charts and find some insights from the visualization

EXAMPLE 3: Small Multiples

What Changed Here?

  • size= — mapped population to point size
  • alpha= — added transparency
  • facet_wrap() — split into one panel per continent
  • labs() — added a subtitle
  • theme() — moved the legend
  • None of this is new syntax — it’s the same grammar, just more layers

EXAMPLE 4: Grouped Bar Chart

With a partner, try to understand what’s happening in this code

gapminder07_grouped <- gapminder07 |>
  mutate(life_exp_bracket = case_when(
    lifeExp < 50 ~ "Under 50",
    lifeExp < 60 ~ "50–60",
    lifeExp < 65 ~ "60–65",
    lifeExp < 70 ~ "65–70",
    lifeExp < 75 ~ "70–75",
    TRUE ~ "75+"
  )) |>
  mutate(life_exp_bracket = factor(life_exp_bracket,
    levels = c("Under 50", "50–60", "60–65", "65–70", "70–75", "75+"))) |>
  group_by(continent, life_exp_bracket) |>
  summarize(pop = sum(pop))

EXAMPLE 4: Grouped Bar Chart

With a partner, try to understand what’s happening in this code

gapminder07_grouped |>
  ggplot(aes(x = reorder(continent, -pop, sum), y = pop, fill = life_exp_bracket)) +
  geom_col(position = "dodge") +
  scale_y_continuous(labels = scales::label_comma()) +
  scale_fill_brewer(palette = "Blues") +
  labs(
    title = "Africa Trails, Europe and Oceania Lead in Life Expectancy",
    subtitle = "Population by continent, broken out by life expectancy group (2007)",
    x = NULL, y = "Population", fill = "Life Expectancy"
  ) +
  theme_minimal() +
  theme(legend.position = "top", plot.title = element_text(face = "bold"))

EXAMPLE 4: Grouped Bar Chart

What Changed Here?

  • fill = — assigned a bar to each life expectancy group within a continent
  • scales::label_comma() — adds comma separators to y-axis numbers
  • position = "dodge" — this is what makes it a grouped (clustered) bar chart — bars sit side by side instead of stacking
  • scale_fill_brewer() — swapped in a color palette
  • theme — moved location of legend and bolded title

R Summary

R vs RStudio

  • Console, Terminal — run code
  • Editor — write scripts and notebooks
  • Environment, History — current objects, past commands
  • Files, Plots, Packages, Help — everything else

R File Types

  • .R — a plain script
  • .Rmd — code + text (we’ve been using a .qmd file all along!)
  • .Rproj — the project file
  • .csv — raw / processed data
  • .html / .pdf — rendered output
  • .RDS — a single saved R object (vs. .RData, which saves your whole environment)

R Project Structure

my-project/
├── my-project.Rproj
├── data/
│   ├── raw/
│   └── processed/
├── R/
│   └── functions.R
├── scripts/
│   ├── 1_clean.R
│   ├── 2_transform.R
│   └── 3_plot.R
├── report.qmd
└── run_all.R

Best Practices

  • Naming:
    • snake_case is the R convention — not camelCase
  • Code Hygiene:
    • Comment the why, not just the what
    • Consistent spacing (x <- 5, not x<-5)
  • Reproducibility:
    • Restart R often and re-run top to bottom
    • If it doesn’t run in a fresh session, it’s not done

Q1: Why do we use GitHub?

  • Version control — a safety net — nothing is ever truly lost
  • Collaboration — multiple people can edit without overwriting each other
  • Portfolio — your GitHub is often the first thing an employer looks at

Q2: What is branching?

  • A fork is when you copy an existing repo under your own account
    • This is used when you don’t have permissions to interact with the original repo
  • A branch is when you create your own side task within a repo
    • You’re not editing the main branch directly and can incorporate back in when needed
    • This is used if everyone is closely working on a project
  • A pull request asks someone to merge your fork or branch back in

Q3: What happens after I submit a pull request?

  • The owner of the original repo can accept or reject your changes
  • DEMO: bootcamp-2026 repo

Q4: What are repo best practices?

  • README — the front door of a repo, written in Markdown
  • Sensible folder structure — README at the root, data separate from code
  • .gitignore — set up before your first commit to avoid hidden files
  • License — add a license like MIT for people to use your code
  • Avoid uploading data — especially large data sets, add links to data or just show results instead of saving in repo

Q5: What should my repo look like for job applications?

  • README does 90% of the work — what, why, key findings, how to reproduce
  • Include easily viewable, rendered outputs and graphics, not just source code
  • Content ideas:
    • A real question vs a built-in / Kaggle data set
    • A topic you’re excited to talk about and break down in interviews
